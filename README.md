# Site Monitor (FastAPI + AsyncIO)

Профессиональный сервис для мониторинга доступности сайтов. Построен на современном асинхронном стеке Python.

## Основные возможности (Фичи)
- **Асинхронный движок**: Максимальная производительность благодаря `asyncio` и `aiohttp`.
- **JWT-авторизация**: Защита API конечных точек с помощью токенов.
- **Фоновый воркер**: Встроенный воркер для регулярных проверок статуса сайтов.
- **История проверок**: Сохранение результатов каждой проверки (статус, время ответа) в базу данных.

## Стек технологий
- **FastAPI** — высокопроизводительный веб-фреймворк.
- **SQLAlchemy 2.0 (Async)** — современный ORM для работы с базой данных в асинхронном режиме.
- **PostgreSQL** — надежная реляционная база данных.
- **Alembic** — инструмент для управления миграциями.
- **Aiohttp** — асинхронный HTTP-клиент для проверки сайтов.
- **Docker & Docker Compose** — контейнеризация и оркестрация.

## Быстрый запуск

1. Склонируйте репозиторий:
   ```bash
   git clone <url>
   cd site-monitor
   ```

2. Запустите приложение с помощью Docker Compose:
   ```bash
   docker compose up --build
   ```
   *При запуске автоматически поднимется база данных PostgreSQL, применятся миграции Alembic и стартует сервер Uvicorn.*

3. API будет доступно по адресу: `http://localhost:8000/docs`

## Архитектурные решения и Trade-offs

### Встроенный asyncio-воркер в lifespan vs Celery + Redis

В проекте используется встроенный фоновый воркер, запускаемый в событиях жизненного цикла FastAPI (`lifespan`), вместо популярного тяжелого стека вроде **Celery + Redis + RabbitMQ**. 

**Почему был сделан такой выбор:**
1. **Простота и легковесность:** Для задачи периодического пинга сайтов не требуется сложная маршрутизация задач или приоритезация очередей. Встроенный `asyncio.Task` отлично справляется с этим, не добавляя внешних зависимостей.
2. **Меньше точек отказа:** Отказ от Redis и Celery снижает инфраструктурную сложность. Нам не нужно мониторить и поддерживать два дополнительных сервиса.
3. **Эффективность ресурсов (I/O Bound):** Проверка сайтов — это типичная I/O задача. Модель конкурентности `asyncio` позволяет одновременно проверять тысячи сайтов в рамках одного процесса с минимальными накладными расходами на память и CPU.
4. **Консистентность кода:** Воркер делит один контекст приложения и пулы соединений базы данных с самим API, что упрощает управление ресурсами и конфигурацией.

**Trade-offs (чем мы пожертвовали):**
- Нет встроенной панели мониторинга задач (как у Celery Flower).
- В случае горизонтального масштабирования (несколько инстансов API) воркеры будут дублировать проверки, если не добавить механизм распределенных блокировок (например, Advisory Locks в PostgreSQL). Однако для MVP и монолитной архитектуры текущее решение является наиболее оптимальным.
