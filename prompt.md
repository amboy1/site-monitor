Ты работаешь над проектом Async Site Monitor на Python.

Контекст проекта:
- FastAPI
- aiohttp
- Pydantic
- asyncio
- pytest
- pytest-asyncio
- SQLAlchemy/PostgreSQL пока НЕ используются
- Проект находится на этапе Stage 1

Текущая функциональность:
1. GET /
2. POST /api/v1/check
3. POST /api/v1/check/batch
4. async-функция check_site()
5. Pydantic-схемы CheckRequest, CheckBatchRequest, CheckResponse
6. timeout передаётся в aiohttp.ClientTimeout
7. batch-проверка выполняется параллельно через asyncio.gather()
8. FastAPI использует response_model

Задача:
Добавь полноценные автоматические тесты для Stage 1.

ВАЖНО:
- Не добавляй SQLAlchemy, PostgreSQL, Alembic, Redis, Celery/ARQ, JWT или Docker.
- Не переписывай архитектуру проекта без необходимости.
- Не меняй существующее поведение API только ради тестов.
- Не используй реальный интернет в тестах.
- Все внешние HTTP-запросы должны быть замоканы.
- Используй pytest и pytest-asyncio.
- Тесты должны быть понятными начинающему backend-разработчику.

====================================
1. ТЕСТЫ checker.py
====================================

Создай:

tests/test_checker.py

Покрой следующие сценарии:

1. HTTP 200
Ожидаем:
{
    "status": "OK",
    "code": 200,
    ...
}

2. HTTP 404
Ожидаем:
status == "ERROR"
code == 404

3. HTTP 500
Ожидаем:
status == "ERROR"
code == 500

4. Timeout
Смоделируй asyncio.TimeoutError.
Ожидаем:
status == "TIMEOUT"
code == 0

5. Произвольное исключение
Например ConnectionError.
Ожидаем:
status == "FAIL"
code == 0
error содержит информацию об ошибке.

6. Проверка timeout
Убедись, что timeout, переданный в check_site(), действительно используется при создании aiohttp.ClientTimeout.

7. Проверка URL
Убедись, что check_site() вызывает session.get() с переданным URL.

При необходимости используй unittest.mock.AsyncMock / MagicMock / patch.

Не делай реальные HTTP-запросы.

====================================
2. ТЕСТЫ FASTAPI
====================================

Создай:

tests/test_api.py

Используй FastAPI TestClient или AsyncClient — выбери вариант, который лучше соответствует текущей архитектуре проекта.

Протестируй:

1. GET /
Ожидаем HTTP 200.

Проверить:
{
    "message": "Async Site Monitor"
}

2. POST /api/v1/check с валидным URL.

Проверить:
- HTTP 200
- response содержит status
- response содержит time
- response содержит code

Реальный aiohttp-запрос НЕ выполнять.
Замокай check_site().

3. POST /api/v1/check с невалидным URL.

Ожидаем:
- HTTP 422

4. POST /api/v1/check с timeout <= 0.

Ожидаем:
- HTTP 422

5. POST /api/v1/check с timeout > 30.

Ожидаем:
- HTTP 422

6. POST /api/v1/check без timeout.

Убедиться, что используется default timeout = 5.

7. POST /api/v1/check/batch с несколькими URL.

Например 3 URL.

Замокай check_site(), чтобы не было реального интернета.

Проверить:
- HTTP 200
- возвращается список
- количество результатов соответствует количеству URL
- каждый результат соответствует CheckResponse.

8. POST /api/v1/check/batch с пустым списком urls.

Ожидаем:
- HTTP 422

9. POST /api/v1/check/batch с количеством URL больше максимального лимита.

Если сейчас установлен max_length=50:
- отправить 51 URL
- ожидать HTTP 422

10. POST /api/v1/check/batch с невалидным timeout.

Проверить:
- timeout <= 0 → 422
- timeout > 30 → 422

====================================
4. МОКИ
====================================

Особенно внимательно работай с aiohttp.
Не допускается такой подход:

requests.get(...)
aiohttp.ClientSession().get(...)
реальный URL

Тесты не должны зависеть от:

- доступности Google/Yandex/любого другого сайта

- скорости сети
- текущего состояния внешних серверов.

Все внешние зависимости должны быть mocked.
